Overview

Celeste RL trains an agent to play Celeste from the game’s state, pressing only the buttons in its controls menu, on unmodified game physics.

Most of it is Python: a Gymnasium environment, PPO training with Stable-Baselines3 and PyTorch, and experiments whose plans and analyses are committed before the data exists. A small C# plugin for the game’s mod loader lets Celeste step as fast as the agent can act.

The hard part came before any learning. The existing tools ran at about 30 steps a second, and nobody had checked them for the kind of exactness RL needs. Once the environment was fast and verified, the results were mixed, and they’re all reported. Without demonstrations, PPO never cleared Room 1. With seven demonstrations found by a search, training from varied starts beat a fixed start by 22.6 points on held-out states. That did not replicate in Room 2.

Scope so far: Chapter 1 has 20 rooms. Rooms 1 and 2 have been attempted. Neither has reached the project’s 99% held-out reliability target.

The bottleneck

Celeste runs at 60 frames per second. Its community automation tool, CelesteTAS, plays inputs back from a file and reports the game’s state over a local HTTP interface, but it has no endpoint that accepts inputs. So my first bridge appends one input line per step to the file CelesteTAS is playing, then waits for the game to reach that frame. The file always ends at the paused frame, so an input can never land on the wrong frame or play twice.

That bridge is exact, but it’s tied to the game’s clock. Over 1,000 measured steps, one frame advance took 32.6 ms on average: about 30 steps a second. The first PPO experiment used two million transitions per seed. At 30 a second, that’s about 18 hours of collection for one seed, before any learning.

Running the game headless didn’t help. With the mods this setup needs, it crashed in the audio library after a savestate, so the project kept the normal renderer.

Building the environment

The game runs in an isolated copy with three community tools: Everest (the mod loader), CelesteTAS (frame-exact input playback) and Speedrun Tool (savestates). From the agent down to the game:

  1. PythonPPO policyPyTorch and Stable-Baselines3, with a small CNN over the room grid.
  2. PythonGymnasium environmentBuilds observations, computes reward and classifies how each episode ended.
  3. PythonLockstep clientThe same reset() and step() as the slow reference bridge, over a local socket.
  4. C#Lockstep pluginHooks CelesteTAS’s playback loop and replies with the new state after every frame.
  5. GameCeleste with EverestThe normal update with the normal frame length. Physics are never modified.
  • Stepping. When every queued input has been played, the plugin sends the state to Python and waits for the next input instead of the next 60 Hz tick. Only the waiting changes.
  • Actions. 24 on/off inputs matching the game’s controls menu, with pause, quick restart and journal disabled. Inputs are validated in both Python and the plugin, so no TAS command can be injected.
  • Observations. Game state, not pixels: the player’s position, speed, dashes, stamina, timers and movement state for the last four decisions; an 11-channel, 32 × 32 grid of tiles, spikes and hazards around the player; and the last four actions.
  • Resets. A savestate taken one frame before the episode start restores in about 4 ms. If an input starts a loading scene, the plugin waits for loading to finish, so every observation is a frame the agent can act on.
  • Sessions. Each connection belongs to a numbered session. Replies only go to the connection that sent the command, and every pending command has a deadline. Any timeout or malformed reply ends the session, and recovery always goes through a full reset.
  • Provenance. Every training run records its commit, the game build’s file hashes and the observation schema version, and refuses to start if any of them drifts.

Making it fast enough for RL

~85×

About 2,600 frames per second, resets included, up from about 30 per second through CelesteTAS’s HTTP interface.

That speed is what made the experiments possible. The first PPO experiment ran three seeds of two million transitions, about six million in total, in about 6.3 hours on one laptop with the game minimised alongside. Each seed ran as one uninterrupted session with zero bridge faults and zero game relaunches. At the old speed, collection alone would have taken over two days.

Training ran at 421 to 487 steps per second, well below 2,600. The game stopped being the bottleneck; the policy and the PPO updates took most of the time.

Proving the environment was correct

In RL, a subtly wrong environment usually doesn’t crash. It teaches the agent something false, and the results look plausible. So the slow file-based bridge stayed in the project as the reference, and the fast one had to match it.

First PPO experiment: no demonstrations

Before any training, the project committed to trying Room 1 without demonstrations first, on a fixed budget, so the result would be reported whichever way it went. Three seeds of PPO, two million transitions each. The reward was +1 for reaching Room 2, −1 for any failure and a tiny cost per frame, with no shaping.

0 clears

in 50,369 training episodes across three seeds and six million transitions. Every training episode ended in death.

The agent didn’t get further into the room either. Replaying saved checkpoints, the median furthest position was x 76 at every point in training, the same as an untrained network of the same shape. The typical episode walked right, fell into the first pit and died on the spikes. No sampled episode passed x 144 of the 261 needed.

Why it failed

  • The policy never left random play. Its entropy stayed within 7% of the maximum on every seed, close to pressing each button on a coin flip.
  • The critic learned only that everything fails. The value estimate converged to almost exactly −1.00, the return of an immediate failure.
  • It wasn’t capacity. Fitting the same network to a recorded clear reached 99.87% per-input accuracy, so the network and observation can represent a solution.

A day later, an addendum to the report named three things the original had left out. The biggest is the action space: 24 independent on/off inputs that start at probability 0.5 mean a fresh policy holds about twelve buttons every frame, against 2.31 in a recorded clear, and the entropy bonus keeps it there. A second reward with distance shaping was inert too. From the fixed start, every failing episode returned the same value to six decimal places, so the shaping cancelled out of the learning signal. The same configuration without demonstrations scored 0 of 250.

Demonstrations

The next step was to show the agent solutions, without anyone playing the game. A Go-Explore-style search, which replays savestates and reads the room’s tile map, found seven complete clears of Room 1 in 20 to 77 seconds each. They differ in length by 50% and in 6 of 7 openings, so they’re genuinely different routes.

Behavioural cloning on five of them, with two whole routes held out, gave a policy that cleared the room 3 times in 50. On the held-out routes it was worse than simply repeating its own last action: 39.7% of frames exactly right, against 85.5%. It hadn’t learned the room. What it gave PPO was a starting point where successes sometimes happened.

The last row is the important one. Three runs worked and one stood still for 400,000 transitions, from the same clone and configuration at a different point in the random stream. At that variance, a success rate from one run means very little, so the next experiment used matched seeds and many runs.

Room 1: the held-out experiment

The question: does fine-tuning from varied starting states generalise better than fine-tuning from the fixed start? Twelve runs from the same clone were declared before training. Arm A trained from the fixed start. Arm B trained from varied starts, sampled from states the agent had already reached. Seeds 3 to 8 were matched across arms.

Held-out evaluation: 200 frozen states from 11 routes found by separate searches. The evaluation and analysis plan was committed, with its hash, before any checkpoint touched them. Each route counts equally, and the confidence interval resamples whole seeds and whole routes, because neighbouring states on one route aren’t independent.

Varied starts won in all six matched seeds, by 2.2 to 71.4 points, and on all 11 routes. That met every part of the rule declared in advance.

98% → 60%

Why the fixed start isn’t enough. Two policies that scored 98.0% and 98.5% from the fixed start scored 59.7% and 84.6% on an earlier diagnostic set of held-out states. One start can’t tell them apart.

An earlier version of this comparison, 79.9% against 65.1%, used checkpoints picked after the campaign and a held-out file with duplicated states. I withdrew it and replaced it with the matched analysis above. The old numbers stay in the report as an audit trail.

Room 2: the replication

The same matched design in Room 2: a clone of seven Room 2 demonstrations, six matched seeds, and 200 held-out states from 12 separately searched routes. The training plan and the evaluation plan were each committed before their data existed.

The declared rule was not met. Varied starts helped three seeds and hurt three. One varied-start run, seed 25, collapsed during training and scored 47.3%. It stays in the analysis.

What it tells me:

  • The Room 1 gain doesn’t transfer automatically. Room 2’s fixed-start arm already scored 86.8%, which left much less room to improve than Room 1’s 52.2%.
  • Collapse isn’t specific to varied starts. A later training-side run repeated arm A with eight new seeds: 5 of 14 fixed-start runs from the same clone collapsed.
  • Both arms fail in the same place. 93.5% to 99.6% of training deaths land in one stretch: a pit, a spiked block and a spiked gap. Every demonstration crosses it using a spring, and the observation has no channel for springs. Whether that causes the failures is a hypothesis these runs don’t test.

Engineering problems

8 GB

of memory in 4 minutes. Long runs leaked 2 to 6 MB per reset. A memory probe traced it to Everest’s dash-trail render targets, which were never freed when a savestate replaced the level. The plugin now releases them before each reset, and memory stays flat.

  • A seed that wasn’t a seed. Two runs with different seeds produced byte-identical episode logs. Stable-Baselines3’s load() re-seeds torch, NumPy and Python globally with the saved checkpoint’s seed, after the run has seeded itself, so every run that started from a checkpoint used the donor’s random stream. Fixed by re-seeding after loading. The evaluation script got its own --seed for the same reason.
  • A race in the first benchmark. An early 1,000-step probe timed out because a previous playback’s frame number satisfied the new playback’s start condition. That’s why the real bridge tracks numbered sessions instead of trusting frame numbers.
  • Headless mode. It crashed in the game’s audio library after a savestate. Rather than patch around it, the project kept the normal renderer and made stepping fast instead.

What I learned

ML experiments

  • One run’s success rate means little. The same configuration gave 0% and 98.5%.
  • Measure on states the policy never trained from. The fixed start made a 60% policy look like 98%.
  • Commit the plan and the analysis before the data, then report what it finds. Room 2 is published because the plan said it would be.
  • Check how a result was selected. My own preliminary comparison was post-selected, and I withdrew it.

Systems

  • Keep a slow, obviously correct path as the reference for the fast one.
  • Test failure on purpose: drop connections, delay replies, stop reading.
  • Long runs find bugs that short tests can’t. The leak only showed over minutes of resets.
  • Pin everything a result depends on, and refuse to run when it drifts.
